# ЧАСТЬ I. СПЕЦИФИКАЦИЯ

## 1. Продуктовые принципы

Пять правил, которые определяют все решения ниже. Если возникает спор — решает этот
список.

1. **Методика — это данные, а не контент.** Семиуровневая программа описывается один
   раз как структура в базе: дисциплина → уровень → практика → критерий аттестации.
   Видео, тексты и занятия только ссылаются на неё. Каталог видео копируется за месяц.
   Структурированная методика с прогрессией и аттестацией — нет. Это главный актив
   платформы.

2. **Офлайн и онлайн — два интерфейса к одному ядру.** Не два продукта. Занятие в
   парке Камоли Худжанди и урок онлайн-курса ссылаются на одну и ту же запись
   `practices`. Ученик имеет один прогресс независимо от того, где занимался.

3. **Мультитенантность с первого дня.** Худжанд — это первая запись в таблице
   `schools`, а не хардкод. Регион, валюта, язык, часовой пояс — поля, а не константы.
   Добавление Москвы или Дубая позже не должно требовать миграции.

4. **Мультиязычность с первого дня, наполнение — по мере надобности.** Все
   пользовательские тексты хранятся как JSONB `{"ru": "...", "tg": "...", "en": "..."}`.
   Сегодня заполняется только `ru`. Переход на `tg` и `en` не потребует переписывания
   схемы.

5. **Запуск по очереди, архитектура — сразу общая.** Одна база, одна авторизация, один
   репозиторий. Но релизы последовательные: сначала офлайн-контур на живой группе,
   потом онлайн. Курс, снятый до обкатки на людях, снимается вслепую.

## 2. Пользователи и роли

| Роль | Кто | Основные права |
|------|-----|----------------|
| `owner` | Акмал | Всё в своей школе + управление школами |
| `admin` | Администратор школы | Ученики, группы, расписание, платежи |
| `instructor` | Инструктор | Свои группы, посещаемость, аттестации |
| `student` | Ученик | Свой профиль, свой прогресс, свои платежи, купленные курсы |
| `guest` | Лид из WhatsApp | Публичный контент, превью-уроки |

Роль хранится в `profiles.role` и всегда проверяется на уровне БД через RLS, а не
только в UI.

## 3. Технологический стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Фронтенд | Next.js 15 (App Router) + TypeScript | SSR для SEO лендингов, один язык на весь стек |
| UI | Tailwind CSS + shadcn/ui | Быстро, темизируемо под чёрно-золотую айдентику Kungfuman |
| БД + Auth + Storage | Supabase (Postgres 15+) | RLS даёт безопасность на уровне данных; auth по телефону/OTP критичен для Таджикистана |
| Хостинг | Vercel | Нулевой девопс, edge-кэш |
| Видео (РФ/СНГ) | Kinescope | Скорость в РФ, защита от скачивания, подписанные ссылки |
| Видео (мир) | Bunny.net Stream | Дёшево, глобальный CDN |
| WhatsApp | Business API (позже) / вручную на старте | Аудитория Худжанда уже там |
| Аналитика | Plausible или Umami | Без cookie-баннеров, проще с GDPR |

**Почему не готовый LMS (GetCourse, Teachable).** Они закрывают онлайн-курсы, но не
закрывают офлайн-операционку и, главное, не дают хранить методику как структуру. Ты
потеряешь принцип №1. При этом на первые 2–3 месяца GetCourse допустим как костыль для
продаж, пока строится своё — см. этап 3.

**Почему не Unreal Engine.** Твоя экспертиза в UE здесь не применяется до этапа 8.
Веб-платформа — это CRUD и права доступа. UE-модуль разбора формы движения через
видеоанализ — отдельный продукт, к которому имеет смысл идти после того, как наберётся
база учеников и материала.

### 4.3 Триггеры и служебные функции

Файл: `supabase/migrations/00002_functions.sql`.

- `set_updated_at()` — автообновление `updated_at` (триггеры на `profiles`,
  `practice_progress`, `lesson_progress`).
- RLS-хелперы (все `security definer` с фиксированным `search_path = public, pg_temp`):
  `auth_school_id()`, `auth_role()`, `is_staff()`, `is_admin()`,
  `has_course_access(p_course_id)`.
- `consume_session_credit()` — списание занятия с активного абонемента при отметке
  присутствия (триггер `trg_attendance_credit` на `attendance`).

> **Внимание:** для RLS-хелперов `security definer` + фиксированный `search_path`
> обязательны.

### 4.4 RLS-политики

Файл: `supabase/migrations/00003_rls.sql`.

**Принцип:** ученик видит только своё, персонал видит всю свою школу, чужие школы не
видит никто.

RLS включается на всех 26 таблицах. Ключевые правила:

- `schools` — своя школа читается участниками; правит только `owner`.
- `profiles` — сам себя (read/update без смены роли), персонал читает свою школу,
  админ правит всё в школе.
- `student_health` — только сам ученик и персонал школы.
- Методика (`disciplines`/`levels`/`practices`/`practice_criteria`) — читают участники
  школы (`practices` — только `published` или персонал), правит только админ.
- Обучение — ученик видит своё, персонал школы правит.
- Расписание/посещаемость — читают все в школе, персонал правит; ученик видит свою
  посещаемость.
- Онлайн-контент — `courses`/`modules`/`lessons` публичны при `published` или доступе
  через `has_course_access()`; превью-уроки открыты; правит админ. `lesson_progress` —
  сам ученик, персонал читает.
- Деньги — `products`/`prices` читаются активными; `subscriptions`/`payments` — ученик
  видит своё, админ правит.
- `leads` — только персонал; `audit_log` — читает только админ.

> **Проверить обязательно.** После применения политик залогинься тестовым учеником и
> попробуй прочитать чужой профиль, чужие платежи и непревьюшный урок неоплаченного
> курса. Если что-то отдаётся — политика дырявая. Это единственный тест, который нельзя
> пропустить.

## Этап 1. Ядро — 2 недели

Цель: база данных, авторизация, оболочка приложения. Ни одной бизнес-фичи.

Задачи:

1. `npx create-next-app` + TypeScript + Tailwind + shadcn/ui
2. Проект Supabase, применение миграций `00001`–`00003`
3. Генерация типов: `supabase gen types typescript --local > lib/types/database.ts`
4. Auth по телефону + OTP (основной сценарий для Худжанда), email как запасной
5. Триггер создания `profiles` при регистрации нового пользователя
6. Middleware: редирект неавторизованных, разведение по ролям (`student` →
   `(student)`, остальные → `(staff)`)
7. Сид-данные: школа Худжанд, 4 дисциплины, 7 уровней в каждой, твой профиль как `owner`
8. Слой i18n: хелпер `t(jsonb, locale)` с фолбэком на `ru`

**DoD:**

- Регистрируешься по телефону, попадаешь в пустой кабинет
- Тестовый ученик не может прочитать чужой профиль через прямой запрос к API
- Типы TypeScript совпадают со схемой БД

4. Публичная страница программы: дерево уровней, читаемое без регистрации — это будет

**DoD:** заходишь в админку и видишь всю свою методику как структуру. Можешь добавить

## Этап 3. Офлайн-контур — 2 недели

Цель: перестать вести учёт в тетради и в WhatsApp.

Задачи:

1. Площадки (`venues`): набережная Сырдарьи, парк Камоли Худжанди
2. Группы с расписанием (JSONB: день недели + время + длительность)
3. Автогенерация `sessions` из расписания группы на 4 недели вперёд (cron через
   Supabase Edge Function или кнопка в админке)
4. Экран отметки посещаемости — проектировать под телефон и под одну руку. Ты отмечаешь
   людей на набережной в 5 утра, а не за компьютером. Крупные кнопки, работа офлайн с
   последующей синхронизацией
5. Планирование практик на занятие (`session_practices`)
6. Отметка прогресса ученика по практикам прямо с экрана посещаемости
7. Карточка ученика: посещаемость, текущий уровень, прогресс, медданные, история

**DoD:** проводишь реальное утреннее занятие и отмечаешь всех через телефон, не открывая
тетрадь.

## Этап 4. Деньги — 1.5 недели

Цель: абонементы и учёт платежей.

Задачи:

1. Продукты и цены: разовое посещение, абонемент 8/12 занятий, безлимит
2. Оформление абонемента ученику из админки
3. Ручное подтверждение платежа (перевод на Алиф → админ подтверждает → абонемент
   активируется)
4. Автосписание занятий с абонемента (триггер `consume_session_credit` уже в схеме)
5. Дашборд: активные абонементы, заканчивающиеся на этой неделе, должники
6. Экспорт платежей в CSV для бухгалтерии

**Не делать на этом этапе:** автоматическую онлайн-оплату. При 50 учениках ручное
подтверждение занимает 5 минут в день, а интеграция эквайринга — неделю. Автоматизируй,
когда станет больно.

**DoD:** видишь, кто заплатил, у кого сколько занятий осталось, и кто пропал.

## Этап 5. Кабинет ученика — 1.5 недели

Цель: ученик перестаёт спрашивать «а когда занятие» в WhatsApp.

Задачи:

3. Свой абонемент: остаток занятий, дата окончания
4. История посещений
5. PWA: manifest, service worker, установка на домашний экран. Отдельное нативное

**DoD:** ученик ставит иконку на телефон и видит своё расписание и прогресс.

## Этап 6. Онлайн-курсы — 3 недели

Цель: первый продаваемый онлайн-продукт.

Задачи:

1. Аккаунт Kinescope, загрузка видео, подписанные ссылки через `api/media/sign` —

2. Курсы → модули → уроки; каждый урок ссылается на `practice_id`
3. Плеер с сохранением прогресса (`lesson_progress`, обновление раз в 15 секунд)
4. Гейтинг доступа: превью-уроки открыты, остальные — через `has_course_access()`
5. Продающая страница курса: программа, превью-урок, отзывы, цена по региону
6. Сертификат по завершении курса (генерация PDF)

**Что снимать первым.** Курс на базе уровня 1 Цигун, уже обкатанного на живой группе с

учеников, и отснятый материал с утренних занятий.

**DoD:** курс опубликован, куплен, пройден одним реальным человеком не из твоего
окружения.

## Этап 7. Регионы и языки — 2 недели

Цель: вторая школа и второй язык без переписывания кода.

2. Наполнение `tg` (таджикский) для публичных страниц Худжанда — сильный сигнал доверия
   локально
3. Наполнение `en` для международных страниц
4. Отображение цен по региону (`product_prices.region`)
5. Создание второй школы в базе, проверка изоляции данных
6. Онлайн-эквайринг: ЮKassa для РФ (требует РФ-юрлица) или Merchant of Record для мира

**DoD:** открываешь сайт с российского IP — видишь рубли и РФ-контур; с таджикского —
сомони.

## Этап 8. Дальше — после 200+ учеников

Идеи, к которым имеет смысл возвращаться только когда база наберётся:

- **Видеоразбор формы.** Ученик снимает своё выполнение практики, система сравнивает с
  эталоном по ключевым точкам (MediaPipe / Pose Estimation). Вот здесь наконец
  пригодится твой опыт в 3D и UE.
- **Сообщество:** чаты по уровням, совместные челленджи.
- **Программа сертификации инструкторов** (структура федерации из твоей концепции).
- **Мобильное приложение на React Native**, если PWA упрётся в ограничения.
- **Ретриты и офлайн-интенсивы** как отдельный тип продукта.

## 11. Юридическая и платёжная схема

> **Дисклеймер:** это не юридическая и не бухгалтерская консультация. Ниже — карта
> вопросов, которые надо задать специалисту, а не готовое решение. Всё требует проверки
> на месте.

| Рынок | Что нужно проверить |
|-------|---------------------|
| Таджикистан | ИП, местный эквайринг (Алиф, DC, Корти Милли). Самый быстрый путь, начинать с него. |
| РФ | Режим самозанятости (НПД) доступен гражданам РФ и стран ЕАЭС; Таджикистан в ЕАЭС не входит, поэтому этот вариант скорее закрыт без гражданства РФ. Реалистичный путь — ИП в РФ, что имеет требования по резидентству и налогам. Обязательно уточнить у бухгалтера. |
| РФ, данные | ФЗ-152 требует хранить персональные данные россиян на серверах в РФ. При работе на российскую аудиторию это может означать отдельный инстанс БД в РФ. Уточнить у юриста, попадает ли твой сценарий под требование. |
| Мир | Stripe не поддерживает Таджикистан. Merchant-of-record сервисы (Paddle, Lemon Squeezy) принимают платежи от твоего имени и решают вопрос налогов, но имеют свои списки допустимых стран для выплат. Проверить актуальные условия до этапа 7. |

**Вывод для архитектуры:** заложи в схему возможность двух инстансов БД (TJ и RU) с
общим кодом. Поле `schools.country_code` и разделение по тенантам это уже позволяют. Не
реализуй заранее, но не мешай себе.

## 12. Как работать с Claude Code

Файл `CLAUDE.md` в корне репозитория содержит незыблемые правила, стек, команды и стиль
(см. корень репозитория).

**Порядок работы.**

Правильно:

1. Открываешь новую сессию под один этап.
2. Промпт вида: «Прочитай `docs/SPEC.md` разделы 4.2 и 4.4. Реализуй этап 3, задачу 1:
   площадки (venues). CRUD-экраны в `(staff)/venues`.»
3. Проверяешь, коммитишь, идёшь к задаче 2.

Неправильно:

- «Вот спека, сделай платформу». Получишь 40 файлов, половина из которых не работает, и
  не поймёшь, где именно.
- Работа над несколькими этапами в одной сессии — контекст переполняется, качество
  падает.

**Правила гигиены.**

- Один коммит на задачу. Задача не проходит `pnpm typecheck` — не коммитишь.
- Миграции только вперёд. Ошибся — новая миграция, а не правка старой.
- `DECISIONS.md`. Каждый раз, когда отходишь от спеки — записываешь почему. Через три
  месяца не вспомнишь.
- RLS проверяется руками. После каждой новой таблицы — логин тестовым учеником и
  попытка прочитать чужое. Claude Code напишет политики, но не проверит их за тебя.
- Сначала домен, потом UI. Просишь реализовать логику в `lib/domain/` с тестами, потом
  отдельно экран поверх неё. Тогда переделка интерфейса не ломает бизнес-правила.
